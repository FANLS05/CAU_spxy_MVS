# 岩壁裂隙检测应用

从一组照片出发,重建点云,用预训练裂缝分割模型识别 2D 裂隙,再按 COLMAP 相机位姿把
裂隙概率投影回三维点云。浏览器里可以调置信度阈值、查看每条裂隙的长度/宽度/走向,并导出
高亮 PLY、纯裂隙 PLY、CSV 和 JSON。

```
照片 ──► run_pipeline.sh ──► 点云 + 网格 + 88 个相机
                                   │
                                   ▼
                    逐张照片裂缝分割 (ONNX, GPU/CPU)
                                   │
                    投影 + 遮挡剔除 + 多视角平均
                                   ▼
                    逐点 score ──► 浏览器阈值高亮
                                   │
                    连通域 / PCA ──► 裂隙属性 + 导出
```

---

## 1. 快速开始

整套应用只依赖 `basic_env`(Python 3.10),不需要 SAM 3。
依赖:`numpy scipy pillow open3d onnxruntime-gpu fastapi uvicorn`(basic_env 里已经装好)。

检测默认走 GPU(onnxruntime-gpu + CUDA 12/cuDNN 9),没有可用 GPU 时自动退回 CPU;
GPU 的 cuDNN/CUDA DLL 复用本机 conda 环境里的 torch cu128(见 2.3 节)。

```powershell
cd D:\code\point_cloud\0916

# 启动本地 Web 应用(自动开浏览器)
& C:\Users\FANLS\.conda\envs\basic_env\python.exe tools\crack_app\server.py

# 不想自动开浏览器 / 换端口
& C:\Users\FANLS\.conda\envs\basic_env\python.exe tools\crack_app\server.py --no-browser --port 8765
```

打开 <http://127.0.0.1:8765>。

界面分三块:

- **左栏**:重建、检测参数(含模型选择)、检测记录列表、显示参数、分析与导出。
- **中间**:Three.js 三维视图,可在「点云 / 网格」之间切换;左键旋转、中键平移、滚轮缩放(右键留给浏览器)。
- **右栏**:裂隙列表、2D 叠加图;底部是任务日志和进度条(检测、重建、分析、网格准备都会实时更新)。

### 1.1 已有场景

1. 顶部「场景」选 `rock`。
2. 左栏「裂隙检测」勾选模型(Tomt996 的 5 个 seed / CrackEvo / SegFormer-b0 / 集成,

5. 左栏底部出现下载链接(全点云 / 纯裂隙 / 裂隙线 PLY、CSV、JSON 等)。

**检测记录**:每次「开始检测」都会新增一条记录,不会覆盖之前的结果。左侧

「开始时间 · 模型」,比如「2026-11-17 00:02:44 · CrackEvo」),点「改名」可以重命名。
点一条记录即切换为当前记录,点云、裂隙列表、2D 叠加图、分析/导出都作用在当前
记录上;每条记录有各自的 `out/<场景>/<记录>/` 导出目录。

分析结果保存在 `out/<场景>/<记录>/cracks.json`。刷新页面或重新选场景时,如果该
记录分析过,界面会自动载入上次的裂隙列表(阈值取上次分析用的值,所以和当前滑杆
可能不同)。旧版本留下的单个检测结果会在第一次打开时自动迁移成一条记录(名字取
检测时间),旧的 `out/<场景>_cracks.*` 也一起挪到 `out/<场景>/<记录>/`。

### 1.2 点云与网格

「显示」里的「显示对象」在**点云**和**网格**之间切换:

- **点云**:直接显示 OpenMVS 稠密点云,裂隙按逐点分数高亮(阈值、热力图都作用在这里)。
- **网格**:显示 `work/<场景>/mvs/scene_dense_mesh.ply`。原始网格动辄上千万面
  (rock 有 1120 万面),所以首次切换时会按「网格细节」档位做一次**体素聚类降采样**,
  结果缓存在 `work/<场景>/crack/mesh_web*.npz`,之后秒开。网格顶点的颜色从显示点云
  按体素查表转移过来。

「网格细节」五档(首次选某档时后台生成缓存,底部进度条会显示):

| 档位 | 面数 | 缓存文件 | 首次生成 | 说明 |
|---|---|---|---|---|
| 标准 | 约 45 万 | `mesh_web.npz` | 约 8 s | 默认,拖动、旋转最顺 |
| 精细 | 约 150 万 | `mesh_web_high.npz` | 约 30 s | 岩面起伏、裂缝边缘明显更清楚 |
| 超细 | 约 400 万 | `mesh_web_ultra.npz` | 1~2 min | 需要独立显卡,内存约 1 GB |
| 原始 | 原始面数(rock 1120 万) | `mesh_web_full.npz` | 2~5 min | 不再降采样;下载约 280 MB,显存占用大 |
| 贴图 | 原始面数 | `crack/tex_web/` 目录 | 约 1 min | 用 OpenMVS 的实拍贴图代替顶点色,最真实 |

原始档只跳过体素聚类,不改变网格本身,也不影响「原始网格 PLY」下载和分析用的网格。
切档时如果当前在看点云,会记下选择,切到网格时再生效。

**贴图档**走另一条数据路径:直接读 `work/<场景>/mvs/scene_textured.ply`(TextureMesh
的输出),里面每个面带三个角的 UV 和一个贴图编号。PLY 的 UV 是**逐角**的,同一个
顶点在不同贴图/接缝上可能对应不同 UV,所以后台按 (顶点, UV) 去重,把每组拆成独立
的顶点表 + 局部索引;再把 16 张 8192² 的 PNG 图集按 4096²、JPEG 90 重新压一遍,
一起缓存在 `work/<场景>/crack/tex_web/`(rock 约 470 MB),之后网页按贴图编号拆成
16 个 mesh 渲染。第一次切换约 1 分钟,期间进度条显示「生成贴图」。

- 贴图档不做任何降采样,面数和 `scene_textured.ply` 一致。
- 需要先跑过 TextureMesh(完整流程默认会跑);没有 `scene_textured.ply` 时切换会提示
  「没有贴图网格」。
- 坐标约定:OpenMVS 的 UV 是 OpenGL 约定(v=0 是图像底边),Three.js 贴图默认
  `flipY=true`,不要关掉,否则整片曲面会采样到图集空白区。
- 贴图档同样叠加裂隙点云,**网格模式下裂隙不消失**:同一条点云几何以独立材质叠在网格表面,阈值滑杆照样即时生效。
- 左栏底部出现「原始网格」下载链接,导出的是**未降采样的原始 PLY**
  (`scene_dense_mesh.ply`,rock 约 300 MB),可以直接拖进 MeshLab / CloudCompare。

网格降采样只影响网页预览,不影响导出的 PLY,也不影响分析与投影用的网格。

### 1.3 从照片开始

1. 左栏「重建」里填照片文件夹(可点「浏览」逐级选目录),场景名例如 `rock2`。
2. 点「开始重建」,日志会实时显示 `run_pipeline.sh` 的 COLMAP / OpenMVS 输出。
3. 重建结束后场景出现在下拉框;首次打开会自动生成显示预览(几十万到 ~120 万点)。
4. 按上面的步骤检测。

> 重建这一步和原来的 `run_pipeline.sh` 完全一样。已经有 `work/<场景>/` 的话直接检测即可。

#### 重建参数

「重建参数(高级)」展开后可以调(默认值就是 `run_pipeline.sh` 的默认值):

| 界面选项 | 环境变量 | 含义 | 默认 |
|---|---|---|---|
| 特征匹配 exhaustive / sequential | `MATCHER` | 两两匹配最准;顺序匹配快,适合视频抽帧 | exhaustive |
| COLMAP 阈值 放宽 / 官方 | `COLMAP_RELAXED` | 放宽 SIFT/匹配/注册阈值,弱纹理更容易成功 | 放宽 |
| 稠密层级 | `RESOLUTION_LEVEL` | OpenMVS 稠密重建降采样层级,0=全分辨率(最细最慢) | 1 |
| 最大边长 | `MAX_RESOLUTION` | 特征提取和稠密重建的最大图像边长 | 2000 |
| 网格细化 | `DO_REFINE` | 是否跑 RefineMesh | 开 |
| 网格精度 | `MESH_MIN_POINT_DISTANCE` 等 | 标准 / 精细 / 极细,见下方「网格更精细」 | 标准 |
| 细化面数上限 | `REFINE_MAX_INPUT_FACES` | 输入网格超过这个面数就跳过 RefineMesh(防 OOM) | 4000000 |

**改了 COLMAP / 稠密参数必须勾选「强制重跑已完成的步骤」**。脚本按输出文件是否存在
跳过步骤,不强制的话参数不会生效。只改网格参数则勾「只重做网格(复用稠密点云)」
(`MESH_FORCE=1`):它会删掉旧网格/纹理,复用已有的稀疏和稠密点云,跳过最慢的稠密重建。

这些参数也可以直接用在命令行(`RESOLUTION_LEVEL=0 MATCHER=sequential ./run_pipeline.sh ...`)。

#### 网格更精细

按对网格细节的影响从大到小:

1. **稠密点云本身**——这是上限。`RESOLUTION_LEVEL=0`(全分辨率)和更大的
   `MAX_RESOLUTION` 能让稠密点云多好几倍点,网格自然会细很多,但也最慢;
   网格算法再细也补不出点云里没有的细节。
2. **`MESH_MIN_POINT_DISTANCE`**(`ReconstructMesh -d`,默认 1.5 像素):
   两个三维点的投影距离小于它就不再连边。调到 0.75 / 0.5 会大幅增加面数。
3. **`REFINE_MAX_FACE_AREA`**(`RefineMesh --max-face-area`,默认 16):
   投影面积大于它的面会被继续细分。调到 8 / 4 细节更好,耗时按面数线性增长。
4. **`REFINE_SCALES`**(默认 1):多尺度迭代次数,2 更细但明显更慢。
5. **`MESH_TARGET_FACES`**(默认 0 = 不限制):给了正数反而会**抽稀**到该面数,
   只在想控制文件大小时用。

| 界面 | `MESH_MIN_POINT_DISTANCE` | `REFINE_MAX_FACE_AREA` | `REFINE_SCALES` | 面数(估算) | 耗时(估算) |
|---|---|---|---|---|---|
| 标准 | 1.5 | 16 | 1 | 基准 | 基准 |
| 精细 | 0.75 | 8 | 1 | ≈ 2~3× | ≈ 2~3× |
| 极细 | 0.5 | 4 | 2 | ≈ 4~6× | ≈ 4~8× |

> 网页显示和导出的「原始网格」用的是 `scene_dense_mesh.ply`,也就是 step 5
> `ReconstructMesh` 的输出 —— 所以 `MESH_MIN_POINT_DISTANCE` 直接决定你在网页里
> 看到的网格细节。`RefineMesh` 的 `scene_dense_mesh_refine.ply` 只用于后面的纹理。

**内存上限(实测)。** rock 用 `-d 0.5` 重建出 11,204,989 面,ReconstructMesh 峰值
23.3 GB;紧接着 RefineMesh 加载完网格就报
`OpenCV: Insufficient memory (Failed to allocate 181089336 bytes)` 并被终止,
纹理也没生成。所以脚本默认在输入面数超过 `REFINE_MAX_INPUT_FACES=4000000` 时
直接跳过 RefineMesh(打一行警告,继续用未细化网格做纹理),要硬试就把它设成 0。

同一份 1120 万面网格直接做纹理(跳过细化)是可以的,但也很吃内存:

| 步骤 | 峰值内存 | 耗时 | 产物 |
|---|---|---|---|
| TextureMesh → `scene_textured.ply` | 25.3 GB | 约 14 min | 538 MB PLY + 16 张 8192² PNG(约 1.8 GB) |
| TextureMesh → `scene_dense_texture.glb` | 25.3 GB | 约 16 min | 341 MB GLB + 16 张 PNG(约 1.8 GB) |

25.3 GB / 32 GB 已经很紧,跑的时候别再开检测/其他 OpenMVS,否则可能被系统杀掉。
面数再大就先用 `--decimate 0.25` 抽稀。

另外在 rock 这份数据上,`-d 0.5` 得到的 1120 万面并不比默认的约 1200 万面多 ——
**这份点云已经接近网格算法的分辨率上限,想更细只能去重跑稠密点云**
(`RESOLUTION_LEVEL=0` + 更大的 `MAX_RESOLUTION`),调 `-d` 收益很小。

`MESH_FORCE=1` 会把旧网格/纹理改名为 `*.bak` 再重跑,成功后自动删除;中途失败的话
`.bak` 还在:

```powershell
cd work\rock\mvs; Get-ChildItem *.bak | ForEach-Object { Move-Item -Force $_.FullName ($_.FullName -replace '\.bak$','') }
```

面数涨上去以后:原始 PLY 会大几倍,MeshLab 打开更慢;网页预览会自动降采样到
约 45 万面,不受影响。`ReconstructMesh` 的 `--decimate` 在 v2.4.0 里默认 1(关闭),
不需要手动改。

只想换网格参数时,不用重跑 COLMAP:

```powershell
# 命令行等价做法
MESH_FORCE=1 MESH_MIN_POINT_DISTANCE=0.75 REFINE_MAX_FACE_AREA=8 ./run_pipeline.sh data\rock rock

# 或者删掉旧网格再点「开始重建」
Remove-Item work\rock\mvs\scene_dense_mesh*.ply, work\rock\mvs\scene_textured*, work\rock\mvs\scene_dense_texture.glb -Force
```


脚本输出 `1x3xHxW` → `1x1xHxW` 的 logits,和已有模型一致。换种子模型时只需要把

> 测试过的其他公开模型:`ThakiCloud/Thaki-FacilityVision-CrackSeg-E2`(UNet-R34,CC-BY-4.0)
> 和 `onebeans/segformer_crack_detection`(SegFormer-b0,MIT)在这批岩壁照片上要么把
> 大片岩面判成裂缝,要么几乎全判背景,跨材质泛化不行,所以没放进选项。

模型都在 ONNX Runtime 上跑,`basic_env` 里装的是 `onnxruntime-gpu`:

- 有 CUDA 12 / cuDNN 9 时默认用 `CUDAExecutionProvider`;
- 加载失败或选手动 CPU 时用 `CPUExecutionProvider`,结果一致(数值误差 < 1e-6);
- 界面「裂隙检测 → 推理设备」可以在 GPU / CPU 之间切。

### GPU 推理

RTX 5070 Ti(sm_120,Blackwell)上实测 `onnxruntime-gpu==1.23.2` + CUDA 12.8 可用。
cuDNN 9 / cudart / cuBLAS 的 DLL 直接复用本机 torch cu128 包里的 `torch/lib`,
代码会按下面顺序找:

1. 环境变量 `CRACK_CUDA_DLL_DIR`;
2. 当前环境的 `Lib\site-packages\torch\lib`;
3. `D:\ProgramData\anaconda3\envs\*\Lib\site-packages\torch\lib` 和 `~\.conda\envs\*`。

找到含 `cudnn64_9.dll` 的目录就加进 `PATH`。如果换机器没有 torch,可以装
`pip install nvidia-cudnn-cu12 nvidia-cuda-runtime-cu12`,或直接用 CUDA Toolkit。

单张 9524×6338 原生分块实测:

| 模型 | CPU | GPU | 加速 |
|---|---|---|---|
| Tomt996 (437 块) | ≈ 28 s | ≈ 5.5 s | ×5 |
| CrackEvo (425 块) | ≈ 29 s | ≈ 6.0 s | ×5 |

88 张全跑原生分块从 40~45 分钟降到约 8 分钟。第一次推理会额外花 2~4 s 初始化 CUDA。

### 快速档 vs 原生分块

| | 快速档 | 原生分块 |
|---|---|---|
| 输入 | 整图缩到长边 1024 | 原图切块,25% 重叠 + Hann 加权 |
| 细裂缝 | 会丢一些 | 保留 |
| 速度 (9524×6338) | < 1 s/张(CPU 推理) | CPU:Tomt996 ≈ 28 s/张 (437 块);GPU:≈ 5.5 s/张 |
| 适用 | 调参数、快速预览 | 最终结果 |

界面默认快速档。正式出结果时切「原生分块」,可以先填「只检测前 N 张」试 4~8 张;
88 张全跑原生分块:CPU 约 40~45 分钟,GPU 约 8 分钟。

### 分数怎么来的

对每个 3D 点:

1. 用相机内参 `K`、位姿 `R,t` 投到每张照片的像素 `(u,v)`;
2. 用 OpenMVS 网格做光线投射,剔除被表面挡住的点;
3. 取该像素的裂缝概率 `p`;
4. `score = Σp / 可见视角数`。

阈值滑杆直接作用在 `score` 上。显示端是 GPU shader 的 uniform,拖动即时重绘;
统计栏的「高亮点」来自 256 桶直方图,不遍历百万点。

## 3. 参数

| 参数 | 含义 | 建议 |
|---|---|---|
| 置信度阈值 | 逐点平均裂缝概率 | Tomt996(含 5 个 seed)0.5,CrackEvo 0.3,SegFormer 0.35,集成 0.4 |
| 最短长度 | 连通域主方向长度下限,单位 = 重建单位 | 默认 bbox 对角线的 0.3% |
| 连接半径 | 体素连通半径,把断开的裂缝点接起来 | 默认 bbox 对角线的 0.3%;裂缝断得厉害就加大 |
| 比例尺 | 每个 model unit 多少米 | COLMAP 没有绝对尺度;有标定物时再填 |
| 显示裂隙 | 整体开关裂隙高亮 | 关掉后点云/网格按原始颜色显示,方便核对重建效果 |
| 显示裂隙线 | 把每条裂隙的中心线折线画出来 | 看走向、做标注时用;需要先「分析并导出」 |
| 裂隙线粗细 | 线的屏幕像素宽度(1~8 px) | 默认 3;投影、截图时调粗更清楚 |
| 只显示裂隙点 | 隐藏背景点 | 看整体裂隙分布时用 |
| 热力图 | 按分数黄→红着色 | 关掉则统一用红橙色 |

`长度`、`宽度` 默认是**重建单位**(model units),不是米。COLMAP/OpenMVS 的重建尺度是
任意的,只有给了 `scale_m_per_unit` 才会在 CSV 里多出 `length_m`、`width_m` 两列。

## 4. 产物

检测记录在 `work/<场景>/crack/runs/<记录>/`(记录名默认是检测开始时间
`YYYYMMDD-HHMMSS`;`run.json` 里存显示名、模型、模式等):

| 文件 | 内容 |
|---|---|
| `run.json` | 记录元信息:显示名、开始时间、模型、模式、推理设备 |
| `scores.npz` | `score` float16[N]、`n_visible` uint16[N]、`max_prob` float16[N] |
| `display.npz` | 降采样显示点云:位置 float32、颜色 uint8、分数 uint8、可见次数 uint8 |
| `gallery/` | 每张图的叠加图 `*_overlay.jpg` 和热力图 `*_prob.jpg`(长边 1600) |
| `labels_display.npy` | 显示点云的连通域编号,分析后生成,供前端联动 |
| `meta.json` | 模型、模式、阈值、bbox、逐图统计、gallery 索引 |

场景级缓存(和具体检测记录无关)仍放在 `work/<场景>/crack/`:

| 文件 | 内容 |
|---|---|
| `runs/` | 所有检测记录 |
| `active_run.json` | 当前选中的记录 |
| `mesh_web.npz` | 浏览器用降采样网格(`positions/normals/colors/indices`),「标准」档 |
| `mesh_web.json` | 网格缓存元信息:源文件大小/修改时间、简化参数、面数、耗时 |
| `mesh_web_high.npz` 等 | 「精细 / 超细 / 原始」档的缓存,`.json` 同上 |
| `tex_web/arrays.npz` | 贴图档的顶点/法线/UV(按 (顶点,UV) 去重后分组拼接)和组内三角形索引 |
| `tex_web/meta.json` | 每组贴图编号、顶点区间 `vstart/vcount`、索引区间 `istart/icount`,以及源 `scene_textured.ply` 的大小/修改时间 |
| `tex_web/tex_<i>.jpg` | 降采样到 4096²、质量 90 的贴图,每张 5~10 MB |

导出结果在 `out/<场景>/<记录>/`(每次检测记录各自一套,互不覆盖):

| 文件 | 内容 |
|---|---|
| `cracks.ply` | 全点云;背景保留原色压暗,裂隙按置信度黄→红 |
| `cracks_only.ply` | 只含裂隙点,按连通域上色 |
| `cracks.csv` | 每条裂隙的属性(UTF-8 BOM,Excel 可直接开) |
| `cracks.json` | 同样的属性 + 每条裂隙的折线坐标 `polyline` + 本次分析参数 |
| `cracks_lines.ply` | 每条裂隙的中心线折线:vertex(带颜色)+ edge,每条裂隙一种颜色 |
| `cracks_lines.json` | 折线坐标(按 `crack_id` 分组),`line_length` 是折线实际长度 |
| `cracks_lines.csv` | 折线逐点坐标:`crack_id, seq, x, y, z` |

网格下载(`/api/scene/<场景>/mesh/download`)直接返回 `scene_dense_mesh.ply`,不经过 `out/`。

**裂隙线几何**是在「分析并导出」时从裂隙点云提取的:在 `gap` 体素上建 26 邻接图,
做两次最远点扫描取图的直径(最长骨架路径),再把路径上的体素换成其中点的重心,
最后做一次端点保持的平滑。所以弯的、分叉的裂隙得到的是一条折线而不是 PCA 直线;
折线分辨率约等于 `gap`(默认 bbox 对角线的 0.3%)。`polyline` 的坐标是点云坐标系
(model units),`line_length` 是折线各段长度之和。

网页里勾选「显示裂隙线」会把每条裂隙的折线用彩色画在最上层(不参与深度测试,
所以不会被点云盖住);折线随「分析并导出」自动更新。线宽用 `LineSegments2`
在屏幕空间展开(原生 WebGL 线宽基本锁死 1 px),下面的「裂隙线粗细」滑杆
1~8 px 实时生效,和缩放无关。

CSV 列(`crack_id` 从 1 开始,和界面表格一致):

```
crack_id, n_points, length, width,
orientation_x, orientation_y, orientation_z,
azimuth_deg, elevation_deg,
centroid_x, centroid_y, centroid_z,
mean_score, max_score
```

给了比例尺时追加 `length_m, width_m`。

```powershell
$py = "C:\Users\FANLS\.conda\envs\basic_env\python.exe"
```

## 6. 实测性能

rock 场景:88 张 9524×6338 照片,稠密点云 13,437,637 点。

| 步骤 | 耗时 |
|---|---|
| 读点云 (968 MB) | ~3 s |
| 读网格 + 建 RaycastingScene | ~2 s |
| 单视角投影 + 遮挡剔除 (约 150 万候选点) | 0.5~1.5 s |
| Tomt996 原生分块单张 (437 tiles) | CPU ~28 s / GPU ~5.5 s |
| CrackEvo 原生分块单张 (425 tiles) | CPU ~29 s / GPU ~6.0 s |
| 快速档 88 张总耗时 (含投影/叠加图) | CPU 248 s(GPU 省的是推理,快速档提速有限) |
| 显示点云降采样 (voxel 0.012) | ~2 s |
| 连通域 + 导出 193 MB PLY | ~6 s |
| 网页网格缓存 标准档 (1120 万 → 约 45 万面,体素聚类) | ~8 s |
| 贴图网格缓存 (1120 万面 + 16 张 8192² 图集缩到 4096²) | ~1 min(读 PLY/算法线/按 UV 去重 45 s + 压图 16 s) |

投影只对**落在图像内**的点打射线,所以不会对全部 1340 万点做 88 次 raycast。

## 8. 排错

**模型文件缺失**

```
模型文件不存在: ...\models\crack\tomt996_seed101.onnx
```

重新下载:

```powershell
foreach ($s in 101,202,303,404,505) {
  curl -L -o "models\crack\tomt996_seed$s.onnx" `
    "https://huggingface.co/Tomt996/uavcrack-crack-segmentation/resolve/main/onnx/seed$s.onnx"
}

curl -L -o models\crack\dihao\crackevo_unet_r34_A.onnx `
  https://huggingface.co/Dihao/crackevo-unet-r34/resolve/main/crackevo_unet_r34_A.onnx
```

直连 HF 不通时,把域名换成 `https://hf-mirror.com/`(或在 URL 前加 `https://ghproxy.net/`)。
SegFormer 还要下载 `models/crack/varcoder/` 里的 `config.json`、`pytorch_model.bin`
(见上一节的导出脚本),或者直接跳过它,只留 UNet 模型。

**检测完没有裂隙**

- 先降低阈值(0.3 左右),再降低「最短长度」和「连接半径」。
- 快速档会丢细裂缝,换原生分块试一个子集。
- 确认照片是**去畸变后**的 `dense/images`,不是原始 `data/`。
- 岩壁上的绿色植被、明显阴影可能被误检,属正常。

**重建日志里出现 `OpenCV: terminate handler is called` / `Insufficient memory`,退出码 127**

OpenMVS 某个步骤内存不够被系统终止了。控制台上看不到是哪一步,看
`work/<场景>/mvs/` 下最新的 `*-*.log`,里面有完整命令行和 `PeakWorkingSetSize`。
最常见的是 RefineMesh 吃满 32 GB:

- 输入网格面数 > 400 万时脚本现在会自动跳过细化,继续做纹理;
- 一定要试,先把 `--decimate` 之类的前置抽稀做掉,或换内存更大的机器;
- 纹理(TextureMesh)也吃内存:rock 的 1120 万面网格峰值 25.3 GB。跑纹理时别同时跑
  检测或别的 OpenMVS;面数再大就加 `--decimate 0.2` 先抽稀到 1/5。

**`POST /api/mesh/prepare` 返回 409**

同一时间只允许一个重任务。重建/检测还没结束时,网格预览会排队失败,
等当前任务结束再切到「网格」即可。

**切到「贴图」提示「没有贴图网格」**

`work/<场景>/mvs/scene_textured.ply` 不存在,说明这个场景还没跑 TextureMesh。
勾选「只重做网格」后点「开始重建」即可补跑,不用重做稠密点云(内存要够,见上一节)。

**点云是空的**

场景还没重建完,或 `work/<场景>/mvs/scene_dense.ply` 被 `.gitignore` 清掉了。
重跑 `run_pipeline.sh`。

**端口被占用**

```powershell
& $py tools\crack_app\server.py --port 8770
```

**浏览器很卡**

- 把「点大小」调小。
- 关闭「只显示裂隙点」以外的纹理没有额外开销;真正的大头是 118 万点本身。
- 显示点云是按 voxel 降采样的,原始分数仍保存在 `scores.npz`,导出用全量。

## 9. 限制与免责声明

- 两个模型分别训练于**路面**和**实验室混凝土/岩石试件**,不是现场岩壁;跨材质泛化没有保证。
- 快速档会漏细裂缝;原生分块更可靠但慢 10~20 倍。
- 投影依赖 COLMAP 位姿和 OpenMVS 网格。网格有洞、位姿漂移、运动模糊都会造成误检/漏检。
- 没有绝对尺度;长度、宽度默认是 model units。
- 这是课程项目的研究原型,不能作为结构安全鉴定依据。
